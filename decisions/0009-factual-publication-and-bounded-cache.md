Bounded stale-while-revalidate follow-up on 26 October (owner backlog B1, recorded by the implementation owner under decision 0010): anonymous public HTML stays fresh for 60 seconds after it is stored. From 60 to under 600 seconds after that store time, a colo may serve the stored copy while one background render per page and isolate replaces it. Withdrawn content, or a page that still references a revoked image, can therefore be served from a cached page in each colo for up to 600 seconds after the copy was stored. This applies to the stale request that starts the refresh, to requests that arrive while that refresh runs or while the refresh table is full, and whether or not the refresh succeeds. A refresh that finds the page withdrawn or redirected removes the copy. A failed refresh leaves it until the 600-second bound. A new deploy never reuses an earlier release's copy. Errors, personalized, authenticated and non-allowlisted requests remain uncached. The window is the single `STALE_SECONDS` constant in `apps/storefront/src/server/public-cache.mjs`; shorten it if the owner wants faster withdrawal. This reaches visitors only after an approved Worker deploy.

Delivery addendum on 27 October 2026 (recorded by the implementation owner under decision 0010): product derivatives are lossy WebP chosen by a measured quality search instead of lossless WebP. "Lossless" in the 21 October follow-up described the helper's first implementation; no decision requires it. The binding requirements are unchanged and are the only gates taken from this file and the 21 October performance checkpoint: detailed zoom must retain source detail, list cards receive only their display size, card derivatives stay within about 80–150 KB, and WebP is used only after visual comparison, with a reviewed exception rather than destructive compression where detail suffers. No approved decision sets a numeric fidelity threshold.

The implementation rule, chosen by the implementation owner: each derivative takes the highest step of the ladder 92, 90, 88, 85, 82, 80, 78, 75 that fits its byte budget (150,000 bytes for a card size, the "150 KB" above; 600,000 bytes for a detail-only file) and is at or above a minimum fidelity floor of luma SSIM 0.97 against a same-width Lanczos3 reference. Of these numbers only the card budget is canonical: it applies the "about 80–150KB per normal card derivative" of `docs/STOREFRONT-PERFORMANCE-2026-10-21.md` line 37. The 600,000-byte detail-only budget and the SSIM 0.97 floor are implementation defaults; no approved decision sets them, and a later reviewed change may adjust them. The deployed storefront puts every variant of at most 960 px into the card srcset, so a 960 px file is a card file even when it is also the detail file of a 960 px source, and carries the card budget. SSIM 0.985 at quality 85 or more is recorded per detail file as a preference for the visual comparison; it is not a gate and no one's approval depends on it. A file that fits no step keeps the top step and is flagged. It is approved only through the canonical text's "reviewed exception". That exception is a separate record file written by an independent reviewer, never by the batch writer and never by default. That independence is a procedural rule, not a technical guarantee: the code compares the reviewer's name with `prepared_by` and reads the record's own `independent_of_batch_writer` flag, both supplied with the runner input, so it catches a record that names its own writer but cannot prove who wrote it. The tooling reads it (`performance_exception_file`, outside the output directory with symlinks resolved) and accepts it only when it names the batch writer as someone else, says `independent_of_batch_writer: true`, and has an exact entry for each flagged file: original, width, sha256, bytes and the failed checks. A record with gaps or extra entries is refused. No input flag waives a budget; the earlier `performance_review_accepted` flag is refused (tests in `media-review-records.test.mjs`). Every included derivative also needs an independent visual comparison against its reference, recorded per file before any approval.

Measured on the five held 960 px renditions of the m126234-0015 sample: lossless WebP made 15 files of 4,525,028 bytes, with all ten 640/960 files over the card budget. Under this rule the 15 files are 1,151,242 bytes and all are within budget and floor. Thirteen use quality 92. The dial's 960 px file uses quality 82 (143,740 bytes, SSIM 0.97437, PSNR 37.53 dB); its higher steps were 164,424 bytes at q85 (0.98119), 187,998 bytes at q88 (0.98626, the smallest file at the 0.985 preference), 209,248 bytes at q90 (0.98952) and 232,558 bytes at q92 (0.99208). The box's 960 px file uses quality 90 (147,118 bytes, SSIM 0.97671, PSNR 42.09 dB); q92 was 172,998 bytes (0.98373). That is the measured tradeoff: the dial and box zoom files are softer than a 0.985 file would be, so a phone or zoom view shows slightly smoothed fine texture, in exchange for keeping every card request within budget on the live Worker. A detail-only 960 px file outside the card srcset would avoid it, but needs a storefront release that separates card and detail variants, and until that release the live Worker would put such a file into card srcsets. Encoding is deterministic (pinned options; same input, same bytes). No crop, upscale or colour change; EXIF/GPS are stripped and ICC kept. Nothing was published by this change.
